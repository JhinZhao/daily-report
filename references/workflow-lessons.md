# 日报工作流踩坑复盘

这些是真实事故的抽象版本。遇到"日期可疑 / 内容可疑 / 文件状态不明"时先读一遍，比现场试错便宜。

## 1. 日期错位（最高频、最致命）

**典型事故**：用户说"这是 X 日的内容"，助手写进了 X-1 或 X+1 的文件；或者用户纠正"今天是 27 号"之后，新内容又写进了 26 号的文件。

**根因**：跳过 `date`、或者只跑了一次 `date` 之后凭印象连续操作；更隐蔽的是把对话摘要里的日期元数据（compaction / 会话开始时间）当成真实日期。

**规则**：

- 每个会话第一次处理日报，先 `date "+%Y-%m-%d %A"`。
- **用户纠正过日期后必须重新 `date`**，不能认为"刚跑过了"。
- 写完前再确认一次：目标文件名里的日期 == 这条内容该归属的日期。
- 写错日期比写错内容更严重：错字改一下，日期错会让两天的数据互相污染。发现写错就先恢复原文件，再在正确日期创建/更新。
- 对话摘要/会话元数据里的时间戳一律不可信，只有 `date` 命令的输出可信。

## 2. 跨会话丢数据

**事故**：用户在设备 A 记录的内容，在设备 B 的会话里完全看不到；助手凭会话记忆"补"历史记录，补错了。

**规则**：

- 【记录】必须立刻写入当天的记录文件——文件是跨会话唯一的真相。
- 历史内容一律 `read_file` 从文件读，不要用记忆重建。
- 用户问"上次/那周"的内容时，先 `ls` 看实际有什么文件，再回答。

## 3. 覆盖丢内容

**事故**：某天的日报已经归档（带 frontmatter 的正式日报），用户又补了一条记录，助手 `write_file` 覆盖整个文件，原有的板块、标签、frontmatter 全丢了。

**规则**：

- 写任何文件前先 `read_file` 头几行判断状态：
  - `# YYYY-MM-DD 记录草稿` → 草稿态，可以整理后写回
  - `---` frontmatter → 已归档，**只能 `patch` 追加**，并更新 `updated` 字段
- 用户说"覆盖"才覆盖，没说就只追加。
- 覆盖前 `ls` 确认文件名（用户可能在别的设备已建过当天的文件）。

## 4. 凭空补内容（最容易失信）

**事故**：用户说"下班，给我日报"，助手"顺手"补了大量用户没提过的工作项，还混入了前几天甚至本周的内容。用户直接质疑数据造假。

**规则**：

- 草稿严格限定在**当天**、**用户实际说过**的条目。
- 不合并前几天内容，不用印象补全，不把助手自己做的基础设施工作（工具调试、脚本开发、链路修复）写进用户的业务日报。
- 用户的边界判断标准：**这件事用户能不能向上汇报**。能汇报 → 是工作内容；纯粹是助手能力建设 → 不写。
- 用户强调"只要今天的"时，先怀疑自己是不是越界了，立刻回到当天记录文件核对。

## 5. 乱建文件 / 用错目录

**事故**：助手自己发明了一个"草稿目录"（例如放在 agent 的私有目录下），和用户实际的日报目录不一致；用户后来在真实目录里找不到任何东西。

**规则**：

- 目录一律由步骤 0 的探测或用户明确指定决定，绝不自己发明。
- 探测结果有 `warnings` 时，先跟用户确认再用。
- 目录结构可能被用户调整，**每次写文件前 `ls` 一次**。

## 6. 语义误读

**事故**：用户说"去掉【X】"，助手新增了一条叫"去掉 X"的记录。

**规则**：短指令有固定含义，见主文档「语法模式速查」。"去掉/改为/用这个/归档 X 和 Y/反推"都是精确指令，不要按字面理解。

## 7. 流程顺序错

**事故**：用户说"下班"，助手直接写了正式日报 + 下班标记 + 同步了外部台账；用户本意只是先看一眼。

**规则**：

- **"下班""生成""给我日报" = 只输出预览，不落盘。**
- **"归档""确认""覆盖""用这个" = 才写文件。**
- 写文件是四步：日报文件 → 保留原始记录 → 下班标记 → （可选）外部同步。任何一步没走完，汇报时要说清楚，不能笼统说"归档完成"。
- 用户说"下班归档"这类混合表述时，仍按"先预览、再确认"走——除非用户明确表示不用看。

## 8. 外部同步的静默失败

**事故**：外部台账写入连续多天失败（目标 ID 里一个字符写错），但助手按记忆复制 ID、没做写前校验，直到用户自己发现数据缺失。

**规则**：见主文档第 10 节。要点是——写入前先发一次只读请求验证目标 ID；用字段 ID 而不用字段名；按"日期 + 提交人"查重；同步失败必须如实上报，不能报"已完成"。
