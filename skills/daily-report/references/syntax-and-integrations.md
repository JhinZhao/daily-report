# 语法速查与可选集成

主 SKILL.md 的补充材料。用户下短指令、或启用外部台账同步时读这份。

## 一、短指令语法模式

用户会用很短的话下指令，含义是固定的，不要按字面理解：

| 说法 | 含义 | 操作 |
|---|---|---|
| `去掉【X】` | 删除 X 条目，不留痕迹 | 读文件 → 定位该行 → 删掉。**不要**新增一条"去掉 X" |
| `X 改为 Y` | 替换 X 条目的项目标签/内容 | 读文件 → 定位原行 → 整行替换，不要追加新行 |
| `用这个` | 按紧随其后的完整日报**覆盖** | 按用户给的格式整理 → 写正式日报（不是叠加） |
| `归档 X 和 Y` | X、Y 是两个日期 | 分别读、分别归档，两个文件都要动 |
| `X 日：aaa / Y 日：bbb` | 冒号/逗号前的日期是归属标签 | 分别追加到对应日期的文件 |
| `覆盖 X` | X 是用户明确指定的日期 | 先确认 `X.md` 存在 → 再覆盖 |
| `反推 X` | 该日无记录但有上下文（如周报覆盖） | 据上下文推断生成；不确定处写"待补充" |
| `今天是 X 日` + 内容 | 按 X 归档，即使系统日期不同 | 用户可能跨 0 点或跨设备延续会话；仍要先确认文件状态 |

**日期标签优先级**：用户明确说出的日期 > 系统 `date` 输出。两者不一致时按用户的来，但必须先把目标文件的状态看清楚再写。

## 二、从 git 提交 / 群聊记录整理日报

用户直接贴 git log 或聊天记录让你整理时，**不要一条提交写一行**（会被当流水账）。

- **按主题合并**：同一 feature 分支的多个提交 + 期间的配色/提示/配置微调 → 合成一条："功能名：子点1，子点2，子点3"。
- **同批 bug 修复合并**成一条。
- **Merge commit 不单列**（其实质提交已包含在内）。
- **不要标注"前端/后端"**这类技术分层，一律按项目分节。
- **密度目标**：每个项目 3–5 条，读起来是"干了哪几件事"，不是"提交了几次"。
- **润色成人话**：去掉 `fix(...)` / `feat(...)` 前缀、作者名、时间戳、"今天"；把 commit 式短句改写成完整的记录语句。
- **发版/上线/部署**在提交里看不出来，用户常会单独补一句"X 号有发版"——听到就单独成条，并回头补进当天记录。

## 三、可选：外部台账同步

有些用户会把日报同步到外部表格/数据库（多维表格、Airtable、Notion、内部系统…）。

**默认关闭**：`config.local.json` 的 `external_sync` 为 `null` 时不执行同步，并在归档结果里明说"未同步外部台账"。

启用后遵守以下约束（都是踩过的坑）：

1. **写入前验证目标身份**（base/table/库 ID、字段 ID 等）：先发一次只读请求，确认目标存在再写。ID 写错是最常见的静默失败原因，且报错看起来像网络问题。
2. **字段用 ID 写，不要猜字段名**。
3. **写入前按"日期 + 提交人"查重**：只有新建语义的接口在重试时会造重复记录——先查回当日记录，命中就跳过或改走更新。
4. **读回的列顺序 ≠ 写入的字段顺序**：读回来是数组，别按写入顺序给列贴标签，会张冠李戴，导致"验证"反而误判。
5. **自己分页**：多数接口单页上限 200 且不会提示截断——用 `offset` 循环到返回行数 < 单页上限为止。
6. **只同步用户指定的范围**（例如只同步正式日报，周报/月报不同步；只同步某类项目的条目）。
7. **失败要如实报告**：归档是"正式日报 + 保留原始记录 + 下班标记 + 外部同步"多步操作，任何一步没走完都不能说"归档完成"，要说清哪步失败、正在怎么补。
8. **需要授权时给用户一个可直接点的授权链接**，不要让用户跑命令行；拿到 device code 后继续。

## 四、打包发布相关

如果这个 skill 要被分发或投稿：

- frontmatter 至少保留 `name` / `description` / `version` / `author` / `license` / `platforms` / `metadata.hermes.tags`。
- 不要提交 `config.local.json`（已在 `.gitignore` 里）——里面有用户的本地路径。
- 支持文件放在 `references/`、`templates/`、`scripts/` 下，由 SKILL.md 指路，不要内联进主文件。
